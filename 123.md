## Problem 1 `[STATUS: FIXED]`

**What:** Registration and login events are never written to the Audit Log. After a new user registers and logs in, the `/dashboard/audit` page shows 0 events. Security-sensitive auth events (register, login, logout, failed login, password reset) are invisible in the audit trail.

**File:** `gateway/routers/auth_router.py`

**Fix:** In every auth endpoint that mutates or authenticates a user — `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `POST /auth/refresh`, `POST /auth/password-reset-request`, `POST /auth/password-reset-confirm` — call `log_audit_event(...)` with the appropriate action string, user_id, org_id, IP address, and user-agent. The `log_audit_event` helper already exists in the codebase; wire it up in each of these handlers. For failed logins, log the attempt with `action="login_failed"` and include the email attempted (not the password). For register, log `action="user_registered"` after the user record is committed.

## Problem 2 `[STATUS: FIXED]`

**What:** New user registration grants immediate dashboard access with no email verification step. A user can register with any email address (including a fake one), be redirected to `/dashboard`, and begin using the platform. There is no email confirmation gate.

**File:** `gateway/routers/auth_router.py`, `core/models.py`, `gateway/dependencies.py`

**Fix:** Add an `email_verified: bool = False` column to the `users` table (with Alembic migration). On `POST /auth/register`, send a verification email with a signed time-limited token (use the existing email-sending utility; if none exists, use Python's `smtplib` with the SMTP config already in `.env`). Add a `GET /auth/verify-email?token=<token>` endpoint that validates the token and sets `email_verified = True`. In `gateway/dependencies.py`, add a check in `get_current_user` that raises HTTP 403 with `{"detail": "email_not_verified"}` if the user's `email_verified` is False, except for calls to the verify-email endpoint itself.

## Problem 7 `[STATUS: PARTIAL]`
**Partial-fix note:** `auto_recovery.py` was updated to check for active runs before restoring (active-run wait loop). But the Redis cooldown key (`guardian:cooldown:{file_path}` with 300s TTL) was NOT added. After restore, the hash is still not updated in `threat_detector.py`. Complete the fix: (1) in `threat_detector.py` at the top of the hash-comparison logic, check `redis.get(f"guardian:cooldown:{file_path}")` and skip detection if the key exists; (2) in `auto_recovery.py` after a successful restore, call `redis.set(f"guardian:cooldown:{file_path}", 1, ex=300)` and call `guardian.update_baseline(file_path)`.

**What:** The Guardian system triggers a DB snapshot and restore whenever `api.py`'s file hash changes. After the restore, the restored file's hash is immediately detected as a "tamper" again because the baseline was never updated to match the restored file. This creates an infinite loop: detect → restore → detect → restore, running every 5 minutes indefinitely across both uvicorn workers. The same hash pair appears in 7+ consecutive TAMPER alerts during a single session.

**File:** `aether_os/core/guardian/threat_detector.py` (or wherever Guardian's tamper detection runs)

**Fix:** After a successful DB restore, immediately update the stored baseline hash to match the current file hash of the restored `api.py`. Add a cooldown flag (e.g., a Redis key `guardian:cooldown:{file_path}` with a 300-second TTL) that prevents re-detection within 5 minutes of a restore. Check this cooldown at the top of the tamper detection logic before comparing hashes. Additionally, when a code deployment or intentional file change is made (e.g., via the admin panel), provide an API endpoint `POST /api/guardian/acknowledge-change` that updates the baseline hash, preventing false positives after legitimate changes.

## Problem 8 `[STATUS: FIXED]`

**What:** After every Guardian DB restore, the system runs `alembic upgrade head` which always fails with `ERROR: Multiple head revisions are present for given argument 'head'`. Every Guardian recovery is logged as `partial (alembic=False, db=True)`, meaning the DB schema may be out of sync after any restore.

**File:** `aether_os/core/guardian/` (the recovery/restore procedure), Alembic migration files

**Fix:** Fix the Alembic migration conflict by running `alembic merge heads` to create a single merge migration that resolves the multiple-head issue. In the Guardian restore procedure, replace `alembic upgrade head` with `alembic upgrade heads` (plural) which handles multiple heads, or better: after merging the Alembic heads into a single linear history, `alembic upgrade head` will work correctly. Do not leave the multiple-head state in the migration history.

## Problem 21 `[STATUS: PENDING]`

For runs with 20,000+ Redis events, this makes the pipeline page unresponsive on reconnect.

**File:** `gateway/routers/factory_runs_router.py` (the SSE endpoint), the Redis event replay logic

**Fix:** Track the last-seen event index per client connection using an SSE `Last-Event-ID` header or a query parameter `?since=<event_index>`. When a client reconnects, only replay events after the last known index, not all events from the beginning. The SSE endpoint should accept `Last-Event-ID` per the HTML5 EventSource spec and only send `data:` lines for events at index > last_seen. The Redis LRANGE call should use `LRANGE key <last_seen+1> -1` rather than `LRANGE key 0 -1`. Set the SSE `id:` field on every emitted event to its Redis list index so clients can track position.
